# GGA1C.Sync — контекст для продолжения работы

## Что это

Промежуточный сервер-хаб, объединяющий несколько платформ предприятия. Живёт на Windows
Server 2025 рядом с **Altium Enterprise Server** и **SolidWorks PDM** — именно рядом, потому
что API PDM это COM и требует установленного клиента PDM на той же машине.

Потоки данных:
1. Altium Enterprise Server → **1С** (OData) — компоненты и BOM;
2. **Grist** → буфер этикеток в MySQL → **GoLabel2** для принтера ZX430i;
3. **Grist** → **SolidWorks PDM** (COM API);
4. **SolidWorks PDM** → обратно в **Grist** (в виджет).

Потоки 1 и 4 серверные, им личность пользователя не нужна. Потоки 2 и 3 инициирует человек
из виджета Grist — там и возникает вопрос опознания (см. «Нерешённые решения»).

## Стек (решение принято 2026-10-18)

- **ABP Framework 10.7.0** (LGPL-3.0) — платформа приложения: учётки, права, настройки с
  шифрованием, аудит, фоновые задания, модульность. Подключается как NuGet-пакеты, не форк.
- **Elsa Workflows 3.9.0** (MIT) — движок процессов с сохранением состояния и повторами,
  встраивается в то же приложение. **Пока не подключён** — следующий шаг.
- **Elsa Studio 3.9.0** — визуальный конструктор на Blazor, встроится в Blazor-проект.
- **MySQL 8.4 LTS** + EF Core — одна база и для ABP, и для буфера этикеток. Выбор не
  вкусовой: GoLabel II **не умеет ODBC вовсе**, зато подключается к MySQL своим драйвером
  (см. раздел про GoLabel), а ABP 10.7 тянет официальный провайдер Oracle
  `MySql.EntityFrameworkCore`. MariaDB не подошла: тот же провайдер падает на ней при
  накатывании схемы (`InvalidCastException: DBNull -> Int64`), а Pomelo, который MariaDB
  поддерживает, под EF Core 10 не выпущен. Прежний вариант — SQLite — убран целиком.
- ~~**SQLite** + EF Core — и для ABP, и для буферов этикеток. Отдельная СУБД намеренно не
  поднимается: хаб должен быть одним процессом на машине, где уже работают Altium ES и PDM.
- Интерфейс — Blazor Server, тема **LeptonX Lite** (открытая, не коммерческая).

Почему не n8n / Kestra / NiFi: коннектор к PDM обязан исполняться на Windows через COM,
поэтому любая платформа на Node, Java или Rust всё равно звала бы наш C#-процесс по HTTP —
две системы вместо одной. Плюс ресурсы: n8n в простое это 300–500 МБ плюс Postgres, против
116 МБ, которые занимал весь прежний сервис целиком.

## Как запустить

Три переменные окружения обязательны: строка подключения с паролем, ключ шифрования и
сертификат. В `appsettings.json` ни пароля, ни ключа нет намеренно — файл уходит в git.

```
rem пароли лежат рядом с базой, вне репозитория:
rem   C:\GGA1C\mysql-app.txt          - пароль пользователя gga1c_app
rem   C:\GGA1C\mysql-root.txt         - пароль root MySQL
rem   C:\GGA1C\stringencryption.key   - ключ шифрования настроек

set ConnectionStrings__Default=Server=127.0.0.1;Port=3306;Database=gga1c;User ID=gga1c_app;Password=<из mysql-app.txt>
set StringEncryption__DefaultPassPhrase=<из stringencryption.key>

cd src\GGA1C.Sync.DbMigrator
dotnet run -c Release

set ASPNETCORE_Kestrel__Certificates__Default__Path=C:\GGA1C	ls\gga1c-stand.pfx
set ASPNETCORE_Kestrel__Certificates__Default__Password=gga1c-stand

cd src\GGA1C.Sync.Blazor
dotnet run --no-launch-profile -c Release --urls "https://0.0.0.0:5443;http://0.0.0.0:5080"
```

**MySQL 8.4 стоит службой `MySQL`**, распакован в `C:\GGA1C\mysql`, данные в
`C:\GGA1C\mysql-data`, настройки в `C:\GGA1C\mysql\my.ini`. База `gga1c`, пользователь
приложения `gga1c_app` (у него есть `CREATE USER` и `GRANT OPTION` на `gga1c.*` — это нужно,
чтобы хаб сам выдавал логины печати).

**Грабля на будущее:** если старый процесс хаба ещё жив, `dotnet run` не может перезаписать
dll, сборка падает, а проверка «сайт отвечает» проходит — отвечает **прежний** процесс.
Выглядит как «изменения не применились»; у меня так ушло время на поиск SQLite в уже
переведённом на MySQL хабе. Сначала гасить процесс `GGA1C.Sync.Blazor`.

**`--no-launch-profile` обязателен.** Без него `dotnet run` берёт адрес из
`Properties/launchSettings.json` (`https://localhost:44397`) и **молча игнорирует** и
`ASPNETCORE_URLS`, и `--urls` — приложение поднимается не там, где его ждёшь, а диагностика
выглядит как «порт не слушается».

Вход: `admin` / `1q2w3E*` (стандартная сеялка ABP).

## Стенд работает по https (сделано 18.10.2026)

**Зачем.** Виджет в Grist считает PKCE-хеш через `crypto.subtle`, а он доступен только в
защищённом контексте. Для фрейма это значит: защищённым должен быть и сам фрейм, **и все
страницы над ним**, то есть сам Grist. По http вход падал с
`Cannot read properties of undefined (reading 'digest')`, и обойти это адресом виджета или
сертификатом только на хабе нельзя — родительская страница всё равно http.

| Адрес | Что отдаёт | Чем терминируется TLS |
|---|---|---|
| `https://192.168.88.238:8444` | Grist | IIS, сайт `grist-https` → `http://127.0.0.1:8484` |
| `https://192.168.88.238:8443` | Keycloak | IIS, сайт `kc-https` → `http://127.0.0.1:8080` |
| `https://192.168.88.238:5443` | хаб и виджет | сам Kestrel, сертификатом из переменных окружения |

Старые http-адреса (`:8484`, `:8080`, `:5080`) живут: ими ходят скрипты стенда. Хаб с http
теперь отвечает 307 на https, Grist по http уводит на тот же вход.

**Порт 443 намеренно свободен и оставлен Docmost.** Сначала Grist висел на нём, и получалось
скверно: Docmost открывают по голому `http://192.168.88.238`, а браузеры сами подставляют
https — то есть по тому же адресу человек попадал в Grist. Поэтому Grist переехал на 8444
(рядом с его http-портом 8484), а голый адрес остался за Docmost.

**Сертификат** самоподписанный, с SAN на `192.168.88.238`, `127.0.0.1`, `localhost` и имя
машины; срок 5 лет. Лежит в `C:\GGA1C\tls\` — `gga1c-stand.pfx` (пароль `gga1c-stand`, нужен
Kestrel) и `gga1c-stand.crt` (PEM, для доверия). Внесён в доверенные корневые этой машины.
**На другой машине** браузер будет ругаться, пока не импортируешь `gga1c-stand.crt` в
«Доверенные корневые центры сертификации».

**Хаб запускается с сертификатом:**

```
cd src\GGA1C.Sync.Blazor
set StringEncryption__DefaultPassPhrase=<из C:\GGA1C\stringencryption.key>
set ASPNETCORE_Kestrel__Certificates__Default__Path=C:\GGA1C\tls\gga1c-stand.pfx
set ASPNETCORE_Kestrel__Certificates__Default__Password=gga1c-stand
dotnet run --no-launch-profile -c Release --urls "https://0.0.0.0:5443;http://0.0.0.0:5080"
```

**Grist** (`/opt/grist/grist-up.sh`): `APP_HOME_URL=https://192.168.88.238`,
`GRIST_OIDC_SP_HOST=https://192.168.88.238`,
`GRIST_OIDC_IDP_ISSUER=https://192.168.88.238:8443/realms/test`. Плюс в контейнер
монтируется `/opt/grist/stand-ca.crt` и задаётся `NODE_EXTRA_CA_CERTS` — **без этого Grist
не поднимается вообще**: node не доверяет самоподписанному сертификату, discovery OIDC
отваливается по таймауту, и контейнер уходит в перезапуск (симптом в логе:
`RestartShell: initial spawn failed`).

**Keycloak** (`/opt/keycloak-stack/docker-compose.yml`): `KC_PROXY_HEADERS=xforwarded` и
`KC_HOSTNAME=https://192.168.88.238:8443`. Без первого Keycloak не верит
`X-Forwarded-Proto` и выдаёт discovery с http-адресами (проверено), а issuer в токене тогда
не совпадает с тем, что ждёт хаб. Теперь issuer — `https://192.168.88.238:8443/realms/test`,
и настройка хаба `Sync.Keycloak.BaseUrl` указывает туда же.

**IIS.** Два сайта на физических папках `C:\inetpub\grist-proxy` и `C:\inetpub\kc-proxy`,
правила ARR в их `web.config` (образец взят у сайта Docmost). Две ловушки:
- серверные переменные `HTTP_X_FORWARDED_*` надо **разрешить сайту**
  (`appcmd set config <сайт> -section:system.webServer/rewrite/allowedServerVariables
  /+[name='HTTP_X_FORWARDED_PROTO'] /commit:apphost`), иначе IIS отдаёт
  **500.50 URL Rewrite Module Error** и ничего больше не говорит;
- `X-Forwarded-For` от ARR содержит порт (`IP:порт`), поэтому во всех правилах он
  переопределяется на `{REMOTE_ADDR}` — на Docmost это в своё время ломало вход.

**Брандмауэр.** Добавлены входящие правила на 443, 8443 и 5443 («GGA1C stand https N»).
Без правила на 8443 Grist из контейнера не доставал до Keycloak: запрос просто истекал.

**Правки клиентов Keycloak:** у `grist` добавлен `https://192.168.88.238:8444/*`, у
`gga1c-widget` — `https://192.168.88.238:5443/widget_report_grist/*` и соответствующие
web origins. Старые http-адреса оставлены на время перехода.

**Настройки виджета в документе** (секция 70): адрес
`https://192.168.88.238:5443/widget_report_grist/index.html`,
`syncServerUrl=https://192.168.88.238:5443`,
`syncKcIssuer=https://192.168.88.238:8443/realms/test`, ключ пуст.

**Грабля bash, на которой я уже спотыкнулся:** комментарий нельзя вставлять внутрь команды
с переносами строк (`docker run ... \`). Оболочка обрывает команду на комментарии, и
`grist-up.sh` падал с `docker run requires at least 1 argument`. Пояснения — только перед
командой.

## Данные и секреты

**База ABP — `C:\GGA1C\Sync.db`**, вне репозитория и вне папки сборки, чтобы переживать
пересборку. Работает в режиме **WAL**, поэтому прочитать её сторонним инструментом на ходу
нельзя — отдаёт `disk I/O error`, читать только копию.

**`StringEncryption:DefaultPassPhrase` в `appsettings.json` пустой намеренно.** Этим ключом
ABP шифрует значения настроек, то есть будущие пароли Altium, 1С и ключи Grist. Шаблон
генерирует ключ и кладёт прямо в файл, который уходит в git — получается, что пароли в базе
зашифрованы, а ключ лежит рядом в репозитории. Реальное значение держится в системной
переменной `StringEncryption__DefaultPassPhrase` и в `C:\GGA1C\stringencryption.key`.
**В репозиторий его не возвращать.**

**Секреты в интерфейсе — маской своей длины**, а не пустым полем с галочкой «сохранено»
(`SecretMask` в Domain.Shared). В поле приходит ровно столько точек, сколько знаков в
значении, поэтому видно, что секрет есть и какой он длины, и его можно выделить и стереть.
Отсюда три исхода при сохранении: одни точки — не менять, пусто — удалить, иное — новое
значение. Прежний вариант («пустое поле = оставить как есть») не позволял удалить секрет
вообще и выглядел как незаполненное поле.

**Шифрованную настройку расшифровывает только `ISettingProvider`.** `ISettingManager`
(`GetOrNullGlobalAsync`) отдаёт её так, как она лежит в базе, то есть шифротекстом, —
записывает он при этом нормально, с шифрованием. Пока секреты не показывались, разницы не
было видно; с масками она вылезла сразу: 128 точек вместо 86. Читать секреты только через
`ISettingProvider` — тем же путём, которым ими пользуются сами клиенты.

## Нерешённые решения (блокируют потоки 2 и 3)

**Как опознавать пользователя в запросе от виджета.** Grist виджету личность не выдаёт:
в plugin API нет `getUser` (проверено), а сессионная кука `grist_core` помечена
`HttpOnly; SameSite=Lax` — из JS не читается и кросс-сайтом не отправляется. Варианты,
которые перебрали: персональные ключи в таблице Grist под правилами доступа (Grist сам
отдаёт каждому только его строку, `user.Email` в ACL это умеет); ключ в `localStorage`
(привязка к браузеру, а не к человеку); проброс хаба через nginx основного Grist — тогда
запрос идёт на тот же хост, несёт сессионную куку, и хаб серверным запросом спрашивает
Grist `/api/session/access/active`, кто это. **Решение не принято.**

Важная деталь на будущее: кука Grist ставится **без атрибута `Domain`**, то есть host-only.
Поддомен вида `sync.mp-lab.ru` её не получит — только тот же хост по другому пути.

**TLS.** Grist в бою работает по https, а хаб получит локальный IP без сертификата — браузер
зарежет запрос как mixed content ещё до отправки. Это проверено вживую: кнопка синхронизации
падала в `Failed to fetch`, а в логе сервера было пусто, ни POST, ни preflight. Варианты:
проброс через nginx Grist (сертификат хабу не нужен вовсе), внутренний УЦ с раздачей
корневого сертификата по групповым политикам, либо полный отказ от вызовов из браузера.

**Буферы по пользователям.** Требование: у каждой учётки свой буфер — папка со своей базой.
Это заодно снимает проблему, что `replace-all` затирает партию другого оператора. Ближайшая
готовая реализация той же идеи — многотенантность ABP в режиме «база на арендатора», где
резолвер выбирает строку подключения на каждый запрос; паттерн стоит позаимствовать, саму
многотенантность включать незачем — организация одна.

**Несколько клиентских GoLabel.** Экземпляров GoLabel2 несколько, стоят на клиентских
машинах, копий серверных файлов на них быть не должно. GoLabel2 **32-битный** (проверено по
установщику V2.1.3: `MSI Template = Intel;1033`), поэтому нужен 32-битный ODBC-драйвер и DSN,
созданный через `C:\Windows\SysWOW64\odbcad32.exe` — DSN из 64-битного администратора
приложение не увидит. Существенно: 32-битный `Microsoft Text Driver (*.txt; *.csv)` входит в
Windows штатно, а SQLite ODBC надо ставить руками на каждую машину — поэтому отдавать
клиентам CSV-выгрузку дешевле и безопаснее, чем сам файл базы.

## Грабли окружения

**ABP CLI не умеет докачивать.** Шаблон тянется одним запросом, и при обрыве SSL CLI падает
со стеком, не оставляя ничего в кэше. На этой машине канал рвётся на длинных загрузках — та
же болячка, что с Docker Hub. Шаблон скачан `curl` с `--retry 5 --retry-all-errors` и лежит
локально: `C:\abp-template\app-10.7.0.zip`. Переигрывать шаблон — через `-ts` на этот файл.

**Уязвимости из шаблона закрыты.** Шаблон тянет `System.Security.Cryptography.Pkcs` и `.Xml`
версии 10.0.11 с уязвимостями высокой серьёзности, а Blazor-проект — уязвимый
`Microsoft.AspNetCore.Components.WebAssembly.Server`. Пины на 10.0.13 стоят в `common.props`
(его импортируют 13 из 14 проектов) и в самом Blazor-проекте. Предупреждений стало 4 вместо
76. **При обновлении ABP проверять заново.**

**Пакеты Elsa переименованы.** Актуальные — `Elsa.Persistence.EFCore` и
`Elsa.Persistence.EFCore.Sqlite`. Старые имена `Elsa.EntityFrameworkCore.*` брошены на версии
3.2.4, и поиск по NuGet выдаёт именно их — не подключать. Эталонный набор ссылок для хоста
«сервер плюс Studio» смотреть в
`C:\elsa-core\apps\src\Elsa.Server.Studio.BlazorServer\*.csproj`.

**Справочные клоны на диске** (не наш код, только для чтения): `C:\elsa-core`, `C:\elsa-studio`.
Песочница Elsa «сервер плюс конструктор» поднята на порту **5055**, вход `admin` / `LmpElsa#2026`.

## Обнаруженный API Altium (реверс-инжиниринг через DevTools, НЕ документирован)

- `GET /components/api/tags` — дерево тегов/папок: `{tags:[{guid,name,parentGuid,subTags,count}], totalCount}`
- `GET /components/api/components?fields[]=Id&fields[]=Comment&...&text=&tag={guid}&orderby=&start=0&limit=50`
  — компоненты, жёсткий лимит 50 на страницу. Параметры точно скопированы из реального запроса браузера.
- Структура компонента: `Id (R_...)`, `ItemGUID`, `Comment` (артикул), `Description`, `Manufacturer`, `FootprintName1`,
  плюс кастомные поля `Наименование 1С`, `Наименование`, `Код`.
- Авторизация: form-login `POST /Account/Login` → cookie `.AFSAUTH` + `ASP.NET_SessionId`.

## НЕРЕШЁННАЯ ключевая проблема — пагинация компонентов

**Симптом:** программные запросы с `tag=` и `start=` **всегда** возвращают первые 50 компонентов,
игнорируя оба параметра — даже для тегов с 3 компонентами (Audio).

**Диагностика:**

- Пробовали: ручная установка этой куки со случайным GUID — не помогает (или помогало

  поле шлёт запросы с этими куками напрямую вместо использования собственной программной
  сессии (см. `GetBrowserSession()` / блок в начале `GetAsync`).

(view конкретного компонента? download?) триггерит установку куки на сервере.

## Grist → GoLabel2 (поток 2)

**Как данные доходят до принтера.** Виджет в Grist шлёт партию этикеток в хаб
(`POST /api/grist/labels/replace-all`, опознание — по токену Keycloak), хаб кладёт строки в
таблицу `AppLabels` базы `gga1c`, а GoLabel II забирает их **прямо из MySQL** по логину и
паролю конкретного человека.

**Главное открытие 18.10.2026: в GoLabel II нет ODBC.** Проверено по его собственным
сборкам (`GoLabel.exe`, `QlabelDlg.dll`, `QLabelSDK.dll` в
`C:\Program Files (x86)\GoDEX\GoLabel II`): строка `ODBC` не встречается ни разу, ни в
каком регистре. В диалоге «Подключить базу» есть CSV, Microsoft Access, Excel, **MySQL,
SQL Server и Oracle** — последние три с логином, паролем и кнопкой проверки. Рядом лежит
`MySqlConnector.dll`, то есть к MySQL GoLabel подключается своим драйвером.

Отсюда два следствия, из-за которых поток 2 и переделан:
- прежний план «буфер в файле SQLite + ODBC-DSN на каждой машине» **нереализуем**: GoLabel
  не прочитает SQLite ни через ODBC (его нет), ни иначе (своего провайдера SQLite тоже нет);
- на машине с принтером не нужно **ничего** устанавливать и настраивать: ни драйвера, ни
  источника данных — только вписать адрес, базу, логин и пароль.

**Что настраивается в GoLabel II:** «Подключить базу» → MySQL, сервер — адрес хаба, порт
3306, база `gga1c`, логин и пароль — выданные в интерфейсе хаба, таблица — `my_labels`.

**Разделение по людям держит СУБД.** Человеку выдаётся логин `lbl_<папка>` с правом
`SELECT` **только на представление** `my_labels`; прав на саму таблицу у него нет.
Представление отбирает строки по логину подключившегося:

```sql
CREATE OR REPLACE SQL SECURITY DEFINER VIEW my_labels AS
SELECT l.Date AS date, l.ProductCode AS product_code, ...
FROM AppLabels l JOIN AppLabelClients c ON c.Slug = l.Slug
WHERE c.PrintLogin = SUBSTRING_INDEX(SESSION_USER(), '@', 1) AND c.IsEnabled = 1
```

**`SESSION_USER()`, а не `CURRENT_USER()`** — внутри представления с правами создателя
`CURRENT_USER()` возвращает создателя, и фильтр отобрал бы строки не того человека.

Проверено вживую: двое записали по 2 этикетки через хаб, логин `lbl_user` видит через
представление ровно свои 2 строки из 4, а `SELECT` по таблице получает
`ERROR 1142: SELECT command denied`. Отключённая учётка (`IsEnabled = 0`) перестаёт видеть
даже свои — условие в представлении.

**Доступ к базе печати появляется сам.** При сверке с Keycloak, как только у человека есть
учётка в хабе и почта, создаётся пользователь MySQL с логином-почтой и паролем **1234**,
права — только на представление `my_labels`. Отдельной кнопки «выдать» нет: администратору
нечего нажимать, он просто диктует человеку его почту и 1234.

**Пароль печати хранится** (зашифрованным, как пароли Altium и PDM) и его **можно
посмотреть** — в карточке учётных данных есть «глаз». Это осознанное отличие от ключа
виджета: пароль человек вписывает в GoLabel руками, и его приходится диктовать, а значит
«показывается один раз» означало бы перевыпуск при каждой потере бумажки.

Там же, в карточке, его меняют: кнопка со стрелками подставляет случайный пароль, а
применяется он при сохранении — чтобы случайное нажатие не отрезало человеку печать.
Сохранение выполняет `ALTER USER` в MySQL и запоминает новое значение.

Выгрузка в CSV (`Labels:ExportRoot`, по умолчанию `C:\GGA1C\labels\<папка>\labels.csv`)
работает параллельно: шаблон GoLabel можно привязать либо к базе, либо к файлу. Файл не
требует ни логина, ни пароля — доступ к папке даёт учётная запись Windows.

**Две странности GoLabel II, обе вылеченные со стороны базы.**

*Первая — окно с ошибкой на каждое обновление.* По журналу запросов MySQL видно, что
GoLabel при обновлении делает так:

```
SELECT ... FROM INFORMATION_SCHEMA.TABLES              <- список всех видимых таблиц
SELECT * FROM INFORMATION_SCHEMA.TABLES WHERE TABLE_SCHEMA='gga1c' AND TABLE_TYPE='VIEW'
SELECT * from administrable_role_authorizations        <- БЕЗ имени схемы
```

Последний запрос MySQL ищет в нашей базе, не находит и отвечает `SELECT command denied`
(так он отвечает и когда объекта нет — чтобы не раскрывать содержимое базы). Спрятать
`information_schema` от пользователя нельзя, она видна всем. Поэтому `EnsureViewAsync`
создаёт рядом с `my_labels` пустую заглушку с тем же именем и выдаёт на неё право: запрос
проходит молча и возвращает ноль строк. Цена — в списке таблиц у человека две строки
вместо одной.

*Вторая — подключения не закрываются.* На каждое обновление GoLabel открывает новое
соединение и прежнее бросает: за несколько нажатий набирается десяток спящих сессий.
Ограничить человека `MAX_USER_CONNECTIONS` нельзя — тогда сервер откажет **новому**
соединению, то есть сломается как раз обновление. Прибирает `PrintConnectionWorker`: раз в
две минуты оставляет самое свежее подключение каждого печатающего, остальные спящие (старше
30 секунд) закрывает. Выполняющиеся запросы не трогает, подключения хаба — тоже.
Для этого у `gga1c_app` есть права `PROCESS` и `CONNECTION_ADMIN`.

**Порт 3306 пока закрыт брандмауэром** — доступ только с самого сервера. Когда появится
рабочее место с принтером, добавить правило на 3306 и проверить, что GoLabel подключается
(MySQL 8.4 использует `caching_sha2_password`; MySqlConnector это умеет, по умолчанию
соединение идёт с TLS сервера).

**Запасной выход — CSV.** GoLabel II читает CSV напрямую, так что при недоступной базе можно
выгружать партию файлом. В коде этого пока нет, делать по необходимости.

## Разделение по учётным записям (решено 2026-10-18)

**Сущность `LabelClient`** (`Domain/Labels`): имя, `Slug` (имя учётки, оно же основа логина
печати), `KeyHash`, `KeyPrefix`, `KeyEncrypted`, `IsEnabled`, `LastUsedAt`, связь с Keycloak
(`KeycloakSub`, `Email`), учётные данные Altium и PDM, `PrintLogin`.

**Со стороны виджета** человека опознаёт токен Keycloak (см. раздел про опознание), и хаб
пишет строки с его `Slug`. **Со стороны принтера** — логин MySQL и представление
`my_labels`. То есть разделение проверяется дважды и в обоих случаях не нами: сначала
Keycloak подписью токена, потом СУБД правами.

Ключ учётки (`KeyHash` / `KeyEncrypted`) остался как запасной путь, пока виджеты не
переведены на токены; после перевода его убрать.

**Почему отказались от файлов.** Исходно буфер был отдельным файлом SQLite на человека, и
это объяснялось так: в SQLite нет пользователей, значит единственная защита — права на
папку, а блокировка записи в файле мешала бы соседям. Довод верный для SQLite, но он исчез
вместе с SQLite: GoLabel II не может читать SQLite вообще (нет ODBC), а MySQL даёт и
учётные записи, и построчную фильтрацию. Папки `C:\GGA1C\buffers` больше нет, прежнее
состояние сохранено в `C:\GGA1C\backup\sqlite-before-mysql-20261018.zip`.

**Удаление учётки** убирает и логин печати в MySQL, и её строки из `AppLabels` — чтобы на
сервере не оставалось ни доступа, ни данных.

Управление — страница «Grist → GoLabel2»: создание учёток, ключи, логины печати, счётчик
этикеток, карточка «Буферы» с содержимым таблицы по каждому человеку.

## Учётные данные людей во внешних системах (сделано 2026-10-18)

В карточке учётки (кнопка с человечком в таблице) прописываются **логин и пароль Altium
Designer и SOLIDWORKS PDM** этого человека. Поля в `LabelClient`: `AltiumLogin`,
`AltiumPasswordEncrypted`, `PdmLogin`, `PdmPasswordEncrypted`, `CredentialsUpdatedAt`.

Пароли шифруются в `LabelClientStore.SetCredentialsAsync` и наружу не отдаются никогда:
в ответе они пусты, передаётся только признак «задан» — и пустое поле при сохранении
означает «оставить прежний». То же правило, что у секрета Keycloak; иначе каждое сохранение
формы стирало бы пароль, которого в форме и не было.

Хранить пароль PDM приходится вынужденно: **PDM не умеет ни SAML, ни OIDC**, через Keycloak
в него не войти, а действовать от имени человека без его пароля PDM не позволяет (`LoginAuto`
входит тем, кто уже вошёл на машине, `Login` требует пароль, подмены пользователя нет).
Расшифровка пока нигде не вызывается — она появится вместе с самими потоками 2 и 3.

## Учётки из Keycloak (сделано 2026-10-18)

Люди не заводятся руками: хаб забирает их из Keycloak и каждому сразу выписывает ключ.

**Как ходим в Keycloak.** Служебной учётной записью клиента
(`grant_type=client_credentials`), то есть без чьего-либо пароля. Клиенту в Keycloak нужны
включённая служебная учётная запись **и роль `view-users` из `realm-management`** — без
роли токен выдаётся нормально, а список пользователей отвечает 403, и причина выглядит
непонятной. `KeycloakClient.Hint()` переводит типовые отказы в указания, что именно
поправить. На стенде для этого создан клиент `gga1c-sync`, секрет — в
`/opt/grist/gga1c-sync-secret.txt`.

**Настройки** (`Sync.Keycloak.*`) задаются переменными окружения при первом запуске
(`Keycloak__BaseUrl`, `Keycloak__Realm`, `Keycloak__ClientId`, `Keycloak__ClientSecret`)
и переносятся в хранилище настроек засевом `KeycloakSettingsDataSeedContributor`; секрет
хранится шифрованным. Уже заданные значения не перезатираются, чтобы правка через
интерфейс не отменялась накатыванием миграций.

**Страница `/keycloak`** (пункт меню «Keycloak») — подключение, проверка связи,
синхронизация и короткая таблица «что здесь что»: реалм — отдельное пространство со своими
людьми (`master` служебный), клиент — зарегистрированная программа, а не человек, секрет —
пароль самой программы. Эти три вещи спрашивают каждый раз, поэтому объяснение лежит
прямо на странице. Раньше карточка висела на странице этикеток — это путало: настройка
общая, а не про печать.

**Связь держится по `sub`**, а не по email или логину: их человек меняет, `sub` — нет.
Один раз учётка, заведённая руками, привязывается по email — чтобы не получить вторую
на того же человека.

**Имя папки буфера выводится из фамилии** транслитерацией (`SlugGenerator`), при совпадении
добавляется число: двух Ивановых достаточно, чтобы сломать наивную схему. При смене фамилии
папка **не** переименовывается: путь уже прописан в источнике ODBC на машине с GoLabel2,
и переименование тихо сломало бы печать.

**Главная тонкость — кто отключил учётку.** Включаем обратно только тех, у кого стоит
`SyncDisabledAt`, то есть кого отключила сама сверка. Если этого не различать, следующая
же сверка вернёт доступ тому, кого администратор выключил руками, и отзыв молча отменится.
Проверено на стенде: учётку, отключённую сверкой, вернуло; учётку, отключённую руками,
не тронуло.

**Периодическая сверка** — `KeycloakSyncWorker`: первый тик через минуту после старта,
дальше раз в час. Это не удобство, а требование: ключ на руках у человека сам не истекает,
и без сверки уволенный продолжал бы печатать.

**Грабля, на которой уже обожглись.** Фоновые работники ABP **не открывают единицу
работы**, и репозитории в них падают с `ObjectDisposedException` — причём из интерфейса
тот же код работает, потому что там единицу работы открывает слой приложения. В
`KeycloakSyncWorker` и `AutoSyncWorker` она открывается явно через `IUnitOfWorkManager`.

**Чего ещё нет:** вход в сам хаб по-прежнему локальный (`admin` через OpenIddict), Keycloak
к нему не подключён. И ключи пока не доставляются в виджет автоматически — следующий шаг:
хаб пишет их в таблицу Grist под правилом `user.Email == rec.email`, и виджет читает свою
строку через `fetchTable`. Важно: эндпоинт `/sql` для этого **не годится** — он требует
`canCopyEverything` и ограниченному пользователю отдаёт 403, а не отфильтрованные строки.

## Правила проекта

1. **Все ответы пользователю — на русском.** Он работает в проде на реальном железе,
   тестирует сразу после каждой правки, часто копипастит консольный вывод построчно.
2. **Базы и секреты — вне репозитория и вне папки сборки** (`C:\GGA1C\`), путь абсолютный.
3. **В репозитории только сервис.** Ни виджета Grist, ни инфраструктуры стенда (Grist,
   Keycloak, Docmost), ни вспомогательных скриптов стенда — локальное держать вне git
   (`.local-tools/`, `wwwroot/widget/` — оба в `.gitignore`).
4. **Перед коммитом — сборка.** `dotnet build -c Release` в корне: ноль ошибок и ноль
   предупреждений `NU1902` / `NU1903` (уязвимости).
5. Прежнее правило про бамп версии в `wwwroot/index.html` **отменено** — того файла больше
   нет. Версия теперь одна на решение, в `common.props` (`<Version>`).
