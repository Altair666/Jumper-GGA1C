# GGA1C.Sync — контекст для продолжения работы

## Что это

Промежуточный сервер-хаб, объединяющий несколько платформ предприятия. Живёт на Windows
Server 2025 рядом с **Altium Enterprise Server** и **SolidWorks PDM** — именно рядом, потому
что API PDM это COM и требует установленного клиента PDM на той же машине.

Потоки данных:
1. Altium Enterprise Server → **1С** (OData) — компоненты и BOM;
2. **Grist** → буфер этикеток → **GoLabel2** (ODBC) для принтера ZX430i;
3. **Grist** → **SolidWorks PDM** (COM API);
4. **SolidWorks PDM** → обратно в **Grist** (в виджет).

Потоки 1 и 4 серверные, им личность пользователя не нужна. Потоки 2 и 3 инициирует человек
из виджета Grist — там и возникает вопрос опознания (см. «Нерешённые решения»).

## Стек (решение принято 2026-10-18)

- **ABP Framework 10.7.0** (LGPL-3.0) — платформа приложения: учётки, права, настройки с
  шифрованием, аудит, фоновые задания, модульность. Подключается как NuGet-пакеты, не форк.
- **Elsa Workflows 3.9.0** (MIT) — движок процессов с сохранением состояния и повторами,
  встраивается в то же приложение. **Пока не подключён** — следующий шаг.
- **Elsa Studio 3.9.0** — визуальный конструктор на Blazor, встроится в Blazor-проект.
- **SQLite** + EF Core — и для ABP, и для буферов этикеток. Отдельная СУБД намеренно не
  поднимается: хаб должен быть одним процессом на машине, где уже работают Altium ES и PDM.
- Интерфейс — Blazor Server, тема **LeptonX Lite** (открытая, не коммерческая).

Почему не n8n / Kestra / NiFi: коннектор к PDM обязан исполняться на Windows через COM,
поэтому любая платформа на Node, Java или Rust всё равно звала бы наш C#-процесс по HTTP —
две системы вместо одной. Плюс ресурсы: n8n в простое это 300–500 МБ плюс Postgres, против
116 МБ, которые занимал весь прежний сервис целиком.

## Как запустить

```
cd src\GGA1C.Sync.DbMigrator
dotnet run -c Release

cd src\GGA1C.Sync.Blazor
dotnet run --no-launch-profile -c Release --urls http://0.0.0.0:5080
```

**`--no-launch-profile` обязателен.** Без него `dotnet run` берёт адрес из
`Properties/launchSettings.json` (`https://localhost:44397`) и **молча игнорирует** и
`ASPNETCORE_URLS`, и `--urls` — приложение поднимается не там, где его ждёшь, а диагностика
выглядит как «порт не слушается».

Вход: `admin` / `1q2w3E*` (стандартная сеялка ABP).

## Данные и секреты

**База ABP — `C:\GGA1C\Sync.db`**, вне репозитория и вне папки сборки, чтобы переживать
пересборку. Работает в режиме **WAL**, поэтому прочитать её сторонним инструментом на ходу
нельзя — отдаёт `disk I/O error`, читать только копию.

**`StringEncryption:DefaultPassPhrase` в `appsettings.json` пустой намеренно.** Этим ключом
ABP шифрует значения настроек, то есть будущие пароли Altium, 1С и ключи Grist. Шаблон
генерирует ключ и кладёт прямо в файл, который уходит в git — получается, что пароли в базе
зашифрованы, а ключ лежит рядом в репозитории. Реальное значение держится в системной
переменной `StringEncryption__DefaultPassPhrase` и в `C:\GGA1C\stringencryption.key`.
**В репозиторий его не возвращать.**

**Секреты в интерфейсе — маской своей длины**, а не пустым полем с галочкой «сохранено»
(`SecretMask` в Domain.Shared). В поле приходит ровно столько точек, сколько знаков в
значении, поэтому видно, что секрет есть и какой он длины, и его можно выделить и стереть.
Отсюда три исхода при сохранении: одни точки — не менять, пусто — удалить, иное — новое
значение. Прежний вариант («пустое поле = оставить как есть») не позволял удалить секрет
вообще и выглядел как незаполненное поле.

**Шифрованную настройку расшифровывает только `ISettingProvider`.** `ISettingManager`
(`GetOrNullGlobalAsync`) отдаёт её так, как она лежит в базе, то есть шифротекстом, —
записывает он при этом нормально, с шифрованием. Пока секреты не показывались, разницы не
было видно; с масками она вылезла сразу: 128 точек вместо 86. Читать секреты только через
`ISettingProvider` — тем же путём, которым ими пользуются сами клиенты.

раздачу самого виджета. Удалены `C:\gg1ac\publish`, `C:\gg1ac\wwwroot` и `C:\AltiumSync`

## Нерешённые решения (блокируют потоки 2 и 3)

**Как опознавать пользователя в запросе от виджета.** Grist виджету личность не выдаёт:
в plugin API нет `getUser` (проверено), а сессионная кука `grist_core` помечена
`HttpOnly; SameSite=Lax` — из JS не читается и кросс-сайтом не отправляется. Варианты,
которые перебрали: персональные ключи в таблице Grist под правилами доступа (Grist сам
отдаёт каждому только его строку, `user.Email` в ACL это умеет); ключ в `localStorage`
(привязка к браузеру, а не к человеку); проброс хаба через nginx основного Grist — тогда
запрос идёт на тот же хост, несёт сессионную куку, и хаб серверным запросом спрашивает
Grist `/api/session/access/active`, кто это. **Решение не принято.**

Важная деталь на будущее: кука Grist ставится **без атрибута `Domain`**, то есть host-only.
Поддомен вида `sync.mp-lab.ru` её не получит — только тот же хост по другому пути.

**TLS.** Grist в бою работает по https, а хаб получит локальный IP без сертификата — браузер
зарежет запрос как mixed content ещё до отправки. Это проверено вживую: кнопка синхронизации
падала в `Failed to fetch`, а в логе сервера было пусто, ни POST, ни preflight. Варианты:
проброс через nginx Grist (сертификат хабу не нужен вовсе), внутренний УЦ с раздачей
корневого сертификата по групповым политикам, либо полный отказ от вызовов из браузера.

**Буферы по пользователям.** Требование: у каждой учётки свой буфер — папка со своей базой.
Это заодно снимает проблему, что `replace-all` затирает партию другого оператора. Ближайшая
готовая реализация той же идеи — многотенантность ABP в режиме «база на арендатора», где
резолвер выбирает строку подключения на каждый запрос; паттерн стоит позаимствовать, саму
многотенантность включать незачем — организация одна.

**Несколько клиентских GoLabel.** Экземпляров GoLabel2 несколько, стоят на клиентских
машинах, копий серверных файлов на них быть не должно. GoLabel2 **32-битный** (проверено по
установщику V2.1.3: `MSI Template = Intel;1033`), поэтому нужен 32-битный ODBC-драйвер и DSN,
созданный через `C:\Windows\SysWOW64\odbcad32.exe` — DSN из 64-битного администратора
приложение не увидит. Существенно: 32-битный `Microsoft Text Driver (*.txt; *.csv)` входит в
Windows штатно, а SQLite ODBC надо ставить руками на каждую машину — поэтому отдавать
клиентам CSV-выгрузку дешевле и безопаснее, чем сам файл базы.

## Грабли окружения

**ABP CLI не умеет докачивать.** Шаблон тянется одним запросом, и при обрыве SSL CLI падает
со стеком, не оставляя ничего в кэше. На этой машине канал рвётся на длинных загрузках — та
же болячка, что с Docker Hub. Шаблон скачан `curl` с `--retry 5 --retry-all-errors` и лежит
локально: `C:\abp-template\app-10.7.0.zip`. Переигрывать шаблон — через `-ts` на этот файл.

**Уязвимости из шаблона закрыты.** Шаблон тянет `System.Security.Cryptography.Pkcs` и `.Xml`
версии 10.0.11 с уязвимостями высокой серьёзности, а Blazor-проект — уязвимый
`Microsoft.AspNetCore.Components.WebAssembly.Server`. Пины на 10.0.13 стоят в `common.props`
(его импортируют 13 из 14 проектов) и в самом Blazor-проекте. Предупреждений стало 4 вместо
76. **При обновлении ABP проверять заново.**

**Пакеты Elsa переименованы.** Актуальные — `Elsa.Persistence.EFCore` и
`Elsa.Persistence.EFCore.Sqlite`. Старые имена `Elsa.EntityFrameworkCore.*` брошены на версии
3.2.4, и поиск по NuGet выдаёт именно их — не подключать. Эталонный набор ссылок для хоста
«сервер плюс Studio» смотреть в
`C:\elsa-core\apps\src\Elsa.Server.Studio.BlazorServer\*.csproj`.

**Справочные клоны на диске** (не наш код, только для чтения): `C:\elsa-core`, `C:\elsa-studio`.
Песочница Elsa «сервер плюс конструктор» поднята на порту **5055**, вход `admin` / `LmpElsa#2026`.

## НЕРЕШЁННАЯ ключевая проблема — пагинация компонентов

**Симптом:** программные запросы с `tag=` и `start=` **всегда** возвращают первые 50 компонентов,
игнорируя оба параметра — даже для тегов с 3 компонентами (Audio).

**Диагностика:**
- С реальными куками браузера (скопированными вручную из DevTools) те же запросы **работают
  корректно** (Audio → 3 компонента, не 50). Подтверждено эндпоинтом `/api/diag/raw-request`.
- Значит проблема не в URL/параметрах, а в серверном сессионном контексте.
- Кука `A365_LIBRARYCOMPONENTSAPI_DOWLOAD_SESSION` создаётся браузером (видимо JS SPA при
  первой загрузке `/components`), не через обычный HTTP Set-Cookie на GET-запрос.
- Пробовали: warmup-запросы к `/librarycomponentsapi/api/v1/...` — кука НЕ появляется.
- Пробовали: ручная установка этой куки со случайным GUID — не помогает (или помогало
  частично, финальный статус не подтверждён — последний тест пагинации после этого фикса
  показывал те же 50/50, нужно перепроверить на актуальной сборке).
- Текущий **временный обход**: в Настройках есть поле "Куки браузера" (`AltiumBrowserCookies`
  в `AppSettings`) — пользователь вручную копирует Cookie-заголовок из DevTools раз в ~24ч
  (пока жива ASP.NET сессия), вставляет в поле. `AltiumService.GetAsync()` при заданном этом
  поле шлёт запросы с этими куками напрямую вместо использования собственной программной
  сессии (см. `GetBrowserSession()` / блок в начале `GetAsync`).

**Следующий шаг для решения "по-настоящему":** открыть DevTools, Network, hard refresh
`/components` с нуля, посмотреть **первые 10-15 XHR-запросов** до того как начинает грузиться
список компонентов — один из них должен инициализировать сессионный контекст на сервере.
Особое внимание на `/librarycomponentsapi/...` эндпоинты — предположительно один из них
(view конкретного компонента? download?) триггерит установку куки на сервере.

## Grist → GoLabel2 (новая, отдельная от Altium фича)

**Задача:** сервис держит третью БД-прокладку (`labels.db`) для печати этикеток на принтере
ZX430i через GoLabel2.

**Разделение прав:**
- **Grist** → пишет через наш HTTP API (`POST /api/grist/labels/upsert`, `/replace-all`,
  `DELETE /api/grist/labels/{externalId}`) с заголовком `X-Api-Key` (ключ хранится в
  `AppSettings.GristApiKey`, автогенерируется, можно перевыпустить в UI).
- **GoLabel2** → читает таблицу `labels` через **ODBC** (SQLite ODBC Driver,
  ch-werner sqliteodbc). GoLabel2 — 32-битное приложение (проверено по установщику
  V2.1.3: `MSI Template = Intel;1033`), поэтому нужен 32-битный драйвер и DSN,
  созданный через `C:\Windows\SysWOW64\odbcad32.exe`.

**⚠️ ТРЕБОВАНИЕ, потерянное при передаче контекста (уточнено 2026-08-21):**
экземпляров **GoLabel2 несколько, и стоят они на клиентских машинах**, а не на сервере.
Исходная схема «GoLabel2 открывает `labels.db` напрямую» рассчитана на одну машину и
этому требованию не удовлетворяет:
- SQLite — встраиваемая БД без сервера, сети и учётных записей. Единственный способ дать
  клиенту тот же файл — расшарить папку по SMB, а блокировки SQLite поверх SMB
  ненадёжны (наш `replace-all` переписывает таблицу в транзакции, читатель может
  поймать `database is locked`).
- В той же папке лежит `sync.db` с `AltiumPassword`, `OnecPassword`, `GristApiKey`,
  `AltiumBrowserCookies` (см. `AppSettings`). Шара «только чтение» их не защищает —
  утечка происходит именно через чтение. Папку `C:\AltiumSync` шарить нельзя.
- Галка Read Only в DSN — не гарантия: её наличие зависит от сборки драйвера, и на одной
  машине под одной учёткой правами NTFS сервис и GoLabel не развести (сняв запись,
  отключишь и AltiumSync, который в эту базу пишет).

**Ограничения, заданные заказчиком:** копий промежуточных файлов на клиентских машинах
**не делаем** — все серверные файлы остаются на одном сервере; отдельную клиент-серверную
СУБД (MySQL и т.п.) ради этого поднимать не хотим. Значит клиенты читают данные с сервера
по сети, и вопрос только в том, ЧЕМ читают.

Существенно для выбора: 32-битный `Microsoft Text Driver (*.txt; *.csv)` входит в Windows
штатно (проверено в `HKLM\SOFTWARE\WOW6432Node\ODBC\ODBCINST.INI\ODBC Drivers`), тогда как
SQLite ODBC надо ставить на каждую клиентскую машину руками. Поэтому отдавать клиентам
выгрузку в CSV из расшаренной папки безопаснее и дешевле, чем сам `labels.db`: у CSV нет
блокировок SQLite поверх SMB, файл подменяется атомарно, и на клиентах не нужен ни один
установленный драйвер. `labels.db` при этом остаётся на сервере как рабочее хранилище.

В любом случае `labels.db` надо унести из `C:\AltiumSync` в отдельную папку, иначе шара
открывает клиентам `sync.db` с паролями. Путь сейчас захардкожен в `LabelsDatabase.cs`
(«рядом с основной БД») — нужен отдельный параметр в `appsettings.json`.

**Схема таблицы `labels`** (см. `LabelsDatabase.cs`):
```
id, external_id (UNIQUE), date, product_code, mode_code,
article, name, manufacturer, barcode, qty, extra1, extra2, extra3, updated_at
```
`date` / `product_code` / `mode_code` — то, что реально печатается на этикетке ГКВ-3 и что
шлёт виджет. Остальные поля — generic-набор под другие сценарии, приходят пустыми.
Старые `labels.db` мигрируются автоматически (`ALTER TABLE ADD COLUMN` в `InitSchema`).

**Контракт с виджетом (решено 2026-08-21, поле-в-поле сверено с кодом виджета):**
- Ключ принимается и как `Authorization: Bearer KEY`, и как `X-Api-Key: KEY` — виджет шлёт
  первый вариант, изначальный дизайн API предполагал второй.
- Тело принимается в трёх формах: голый массив, одиночный объект и обёртка
  `{"items":[...]}` / `{"records":[...]}` — виджет шлёт `{"items":[...]}`.
- `externalId` больше НЕ обязателен: если не прислан, собирается как
  `product_code|mode_code`, дубли внутри пачки разводятся суффиксом `#2`.
- Семантика синхронизации — **replace-all**: каждое нажатие «Синхронизация» заменяет
  таблицу целиком, в ней ровно то, что выбрано в виджете сейчас. Поэтому в настройках
  виджета Endpoint = `/api/grist/labels/replace-all` (а не `/upsert`, который стоит по
  умолчанию в самом виджете — см. промт на правки виджета ниже).

**Виджет.** Живёт в отдельном репозитории https://github.com/Altair666/widget_report_grist
(на 18.10.2026 — v0.52.0, деплой на GitHub Pages). Кнопка «Синхронизация» и панель настроек
(⚙: Server URL / API Key / Endpoint) там уже есть, `syncLabels()` шлёт
`{items:[{date, product_code, mode_code}]}`. С v0.52.0 он сам достаёт свой ключ из таблицы
`LabelKeys` (см. ниже) и просит ввести его руками, только если не нашёл.

Копия виджета может лежать и у нас — `wwwroot/widget/index.html`, байт-в-байт из его
репозитория. **В этот репозиторий она НЕ коммитится** (в .gitignore): виджет живёт в своём
репозитории и в сборке основного Grist. Копия нужна только для локальной отладки стенда:
GitHub Pages отдаёт виджет по https, AltiumSync слушает http://…:5000, и браузер режет
такой запрос как mixed content — кнопка «Синхронизация» молча падает в `Failed to fetch`,
до сервера не доходит ничего (в логе запросов пусто — ни POST, ни OPTIONS). Копия с того же
origin, что и API, этой проблемы не имеет. В бою вопрос не встаёт: там виджет отдаётся самим
Grist (db.mp-lab.ru), то есть с того же https-origin, что и страница.

Хаб отдаёт эту копию по адресу **`/widget_report_grist/index.html`** (папка из
`Widget:LocalPath`, по умолчанию `C:\GGA1C\widget`). Адрес повторяет имя репозитория
намеренно: он прописан в настройках секции Grist, и по нему видно, что это именно виджет,
а не страница хаба. В секции Grist стенда стоит
`http://192.168.88.238:5080/widget_report_grist/index.html`.

Копия и скрипт её обновления в репозиторий не входят — здесь только сервис. Скрипт стенда
лежит рядом, вне git: `.local-tools\watch-widget.ps1` (задача планировщика
`AltiumSync-Widget-Watch`, раз в 10 минут: `git fetch` в репозитории виджета, перемотка на
origin, копия в `C:\GGA1C\widget`, проверка отдаваемой версии по :5080).

**Опознание человека: токен Keycloak (решено 18.10.2026, работает).** В документе Grist
хаб не хранит и не пишет ничего — ни ключей, ни таблиц, и прав на запись ему не нужно.
В бою этих прав у него и не будет: у большинства людей в рабочем Grist ограниченный набор
прав, создавать и менять таблицы они не могут.

Как работает: виджет получает у Keycloak токен (код с PKCE на публичном клиенте
`gga1c-widget`) и шлёт его хабу заголовком `X-Keycloak-Token`. Хаб проверяет подпись
открытыми ключами реалма (`/protocol/openid-connect/certs`, ключи кешируются),
издателя, срок и то, что токен выдан именно нашему клиенту (`azp`/`aud`), после чего берёт
из токена `sub` и `email`. Учётку ищет сначала по `sub` — он не меняется при правке почты
и имени, — потом по почте. Проверено вживую: три человека (`a.morozov`, `tester`,
`o.lebedeva`) записали этикетки каждый в свой буфер, Grist в этом не участвовал.

**Клиент `gga1c-widget` — не учётная запись.** Это регистрация приложения: публичный
клиент без секрета, без служебной учётной записи и без ролей, доступа ни к чему он не даёт.
Единственное, что с ним можно сделать — попросить Keycloak впустить человека и выдать токен
на этого клиента; пароль человек вводит на странице Keycloak, виджет его не видит. Хаб
принимает токены только этого клиента (настройка `Sync.Keycloak.WidgetClientId`).
Настройки клиента на стенде: `publicClient`, только `standardFlow` + PKCE S256,
`directAccessGrants` выключен (включал только для проверок с консоли, потом выключил и
убедился: пароль через него больше не принимается), redirect URI ровно один —
`http://192.168.88.238:5080/widget_report_grist/*`, web origin — `http://192.168.88.238:5080`.
**Для боя** добавить адрес, по которому виджет отдаёт рабочий Grist, и убрать стендовый.

**Тупиковые варианты, не переоткрывать:**
- *Ключ в настройках виджета* — настройки секции лежат в документе и общие для всех, кто
  открыл страницу, то есть ключ (как и почта) получается один на всех. Разделения по людям
  не выходит.
- *Почта, вписанная в виджет руками* — это утверждение, а не доказательство: любой назвал
  бы чужой адрес и писал в чужой буфер.
- *Ключи в таблице документа* — лежали бы открытым текстом: их видит всякий, у кого полный
  доступ, и они уезжают в выгрузки и снимки.
- *Таблица почт в документе + токен Grist* (`grist.docApi.getAccessToken`) — работало, но
  требует от хаба прав на запись в документ, которых в бою нет. Побочно выяснилось, что
  правило `user.Email == rec.email` режет выборку и для ключа API хаба: он видит одну
  строку, считает остальных отсутствующими и плодит дубли (шесть с первого тика). Код и
  таблица удалены, документ вернулся к исходному виду.

Приём прежнего ключа учётки (`X-Api-Key` / `Bearer`) оставлен, пока виджет не переведён на
токены Keycloak; после перевода убрать.

## Разделение по учётным записям (решено 2026-10-18)

Разделение идёт **по ключу**: ключ и есть удостоверение, по нему хаб находит учётку и
пишет в её буфер. Альтернативы отпали — Grist не отдаёт виджету личность пользователя
(в plugin API нет `getUser`, сессионная кука `HttpOnly; SameSite=Lax`), а настройки
виджета хранятся в опциях секции **документа**, то есть общие для всех, кто откроет
страницу. Ключ — единственное, что виджет может предъявить достоверно.

**Сущность `LabelClient`** (`Domain/Labels`): имя, `Slug` (имя папки буфера), `KeyHash`,
`KeyPrefix`, `KeyEncrypted`, `IsEnabled`, `LastUsedAt`.

Ключ хранится в двух видах осознанно:
- `KeyHash` — SHA-256, по нему идёт поиск на каждом запросе: одно сравнение, и украденная
  база не отдаёт рабочих ключей;
- `KeyEncrypted` — тот же ключ под шифрованием ABP (ключ шифрования вне репозитория),
  чтобы администратор мог посмотреть значение повторно, а не выпускать новое каждый раз.

**Буфер на учётку**: `C:\GGA1C\buffers\<slug>\labels.db` (корень задаётся
`Labels:BuffersRoot`). Это снимает проблему, из-за которой `replace-all` одного оператора
затирал партию другого, и даёт по файлу на шару для GoLabel2. `Slug` проверяется строго
(только латиница, цифры, дефис, подчёркивание): значение попадает в путь на диске, и
без проверки `..\..\GGA1C` увело бы запись туда, где лежат `Sync.db` и ключ шифрования.

**Перенос со старой схемы** сделан засевом `LabelClientsDataSeedContributor`: при пустой
таблице создаётся учётка «Общий» (slug `shared`) с **прежним** общим ключом из настройки
`Sync.GristApiKey`, а старый файл `buffers\labels.db` переезжает в её папку. Иначе
обновление мгновенно сломало бы уже настроенные виджеты (401) и оставило накопленную
партию в файле, который никто не читает.

**Почему файл на человека, а не одна база с таблицей на каждого.** Вопрос законный, схема
с одним файлом и таблицами (или представлениями) по людям технически работает. Отказались
по четырём причинам, и первая решающая:

1. **В SQLite нет пользователей и прав.** Вся защита файловой базы — это сам файл. Внутри
   одного файла любой, у кого есть источник ODBC, читает все таблицы: разделение остаётся
   косметикой в названиях. Разные папки дают единственный доступный механизм принуждения —
   права NTFS на папку.
2. **Блокировка записи в SQLite на уровне файла.** `replace-all` — это `DELETE` + вставки в
   одной транзакции; на общем файле она встаёт поперёк чтения с принтера соседа, а читающий
   через ODBC — поперёк чужой синхронизации (`SQLITE_BUSY`). С файлом на человека конкуренция
   остаётся внутри одного человека.
3. **Удаление учётки.** Папку удаляем целиком; в общем файле пришлось бы выполнять `DELETE`
   с условием (цена ошибки в условии — чужая партия), а файл после этого всё равно не
   уменьшается.
4. **Повреждение файла** кладёт всех сразу, а не одного.

**Удаление учётки удаляет и папку буфера** — чтобы не копить мусор на сервере. Порядок:
сначала запись в базе, потом файлы; если файл занят (открыт источник ODBC в GoLabel2),
ключ уже отозван, а папка остаётся и видна в интерфейсе как «папка без учётной записи» —
её можно удалить оттуда же.

Управление — страница «Grist → GoLabel2»: создание учёток, показ и перевыпуск ключей,
включение и отключение, счётчик этикеток, путь к файлу для DSN, очистка буфера.
Отключённая учётка получает 401 с отдельным текстом — чтобы отзыв доступа не выглядел
для оператора как «ключ потерялся».

**Карточка «Буферы»** на той же странице показывает содержимое каждого файла: таблица
этикеток (первые 50 строк из `GetTop`, всего — счётчиком), размер, время последней записи
и полный путь для DSN. В тот же список попадают папки без учётки. Без этого буферы были
видны только как число в таблице учёток, и «что сейчас лежит у кого» приходилось смотреть
через ODBC.

## Учётные данные людей во внешних системах (сделано 2026-10-18)

В карточке учётки (кнопка с человечком в таблице) прописываются **логин и пароль Altium
Designer и SOLIDWORKS PDM** этого человека. Поля в `LabelClient`: `AltiumLogin`,
`AltiumPasswordEncrypted`, `PdmLogin`, `PdmPasswordEncrypted`, `CredentialsUpdatedAt`.

Пароли шифруются в `LabelClientStore.SetCredentialsAsync` и наружу не отдаются никогда:
в ответе они пусты, передаётся только признак «задан» — и пустое поле при сохранении
означает «оставить прежний». То же правило, что у секрета Keycloak; иначе каждое сохранение
формы стирало бы пароль, которого в форме и не было.

Хранить пароль PDM приходится вынужденно: **PDM не умеет ни SAML, ни OIDC**, через Keycloak
в него не войти, а действовать от имени человека без его пароля PDM не позволяет (`LoginAuto`
входит тем, кто уже вошёл на машине, `Login` требует пароль, подмены пользователя нет).
Расшифровка пока нигде не вызывается — она появится вместе с самими потоками 2 и 3.

## Учётки из Keycloak (сделано 2026-10-18)

Люди не заводятся руками: хаб забирает их из Keycloak и каждому сразу выписывает ключ.

**Как ходим в Keycloak.** Служебной учётной записью клиента
(`grant_type=client_credentials`), то есть без чьего-либо пароля. Клиенту в Keycloak нужны
включённая служебная учётная запись **и роль `view-users` из `realm-management`** — без
роли токен выдаётся нормально, а список пользователей отвечает 403, и причина выглядит
непонятной. `KeycloakClient.Hint()` переводит типовые отказы в указания, что именно
поправить. На стенде для этого создан клиент `gga1c-sync`, секрет — в
`/opt/grist/gga1c-sync-secret.txt`.

**Настройки** (`Sync.Keycloak.*`) задаются переменными окружения при первом запуске
(`Keycloak__BaseUrl`, `Keycloak__Realm`, `Keycloak__ClientId`, `Keycloak__ClientSecret`)
и переносятся в хранилище настроек засевом `KeycloakSettingsDataSeedContributor`; секрет
хранится шифрованным. Уже заданные значения не перезатираются, чтобы правка через
интерфейс не отменялась накатыванием миграций.

**Страница `/keycloak`** (пункт меню «Keycloak») — подключение, проверка связи,
синхронизация и короткая таблица «что здесь что»: реалм — отдельное пространство со своими
людьми (`master` служебный), клиент — зарегистрированная программа, а не человек, секрет —
пароль самой программы. Эти три вещи спрашивают каждый раз, поэтому объяснение лежит
прямо на странице. Раньше карточка висела на странице этикеток — это путало: настройка
общая, а не про печать.

**Связь держится по `sub`**, а не по email или логину: их человек меняет, `sub` — нет.
Один раз учётка, заведённая руками, привязывается по email — чтобы не получить вторую
на того же человека.

**Имя папки буфера выводится из фамилии** транслитерацией (`SlugGenerator`), при совпадении
добавляется число: двух Ивановых достаточно, чтобы сломать наивную схему. При смене фамилии
папка **не** переименовывается: путь уже прописан в источнике ODBC на машине с GoLabel2,
и переименование тихо сломало бы печать.

**Главная тонкость — кто отключил учётку.** Включаем обратно только тех, у кого стоит
`SyncDisabledAt`, то есть кого отключила сама сверка. Если этого не различать, следующая
же сверка вернёт доступ тому, кого администратор выключил руками, и отзыв молча отменится.
Проверено на стенде: учётку, отключённую сверкой, вернуло; учётку, отключённую руками,
не тронуло.

**Периодическая сверка** — `KeycloakSyncWorker`: первый тик через минуту после старта,
дальше раз в час. Это не удобство, а требование: ключ на руках у человека сам не истекает,
и без сверки уволенный продолжал бы печатать.

**Грабля, на которой уже обожглись.** Фоновые работники ABP **не открывают единицу
работы**, и репозитории в них падают с `ObjectDisposedException` — причём из интерфейса
тот же код работает, потому что там единицу работы открывает слой приложения. В
`KeycloakSyncWorker` и `AutoSyncWorker` она открывается явно через `IUnitOfWorkManager`.

**Чего ещё нет:** вход в сам хаб по-прежнему локальный (`admin` через OpenIddict), Keycloak
к нему не подключён. И ключи пока не доставляются в виджет автоматически — следующий шаг:
хаб пишет их в таблицу Grist под правилом `user.Email == rec.email`, и виджет читает свою
строку через `fetchTable`. Важно: эндпоинт `/sql` для этого **не годится** — он требует
`canCopyEverything` и ограниченному пользователю отдаёт 403, а не отфильтрованные строки.

## Правила проекта

1. **Все ответы пользователю — на русском.** Он работает в проде на реальном железе,
   тестирует сразу после каждой правки, часто копипастит консольный вывод построчно.
2. **Базы и секреты — вне репозитория и вне папки сборки** (`C:\GGA1C\`), путь абсолютный.
3. **В репозитории только сервис.** Ни виджета Grist, ни инфраструктуры стенда (Grist,
   Keycloak, Docmost), ни вспомогательных скриптов стенда — локальное держать вне git
   (`.local-tools/`, `wwwroot/widget/` — оба в `.gitignore`).
4. **Перед коммитом — сборка.** `dotnet build -c Release` в корне: ноль ошибок и ноль
   предупреждений `NU1902` / `NU1903` (уязвимости).
5. Прежнее правило про бамп версии в `wwwroot/index.html` **отменено** — того файла больше
   нет. Версия теперь одна на решение, в `common.props` (`<Version>`).
