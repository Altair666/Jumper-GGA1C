### БАГ-1. GoLabel не входит в MySQL после перезапуска MySQL
**Статус:** исправлено. `PrintLoginCacheWarmer` при старте хаба входит каждым включённым
логином печати по TLS; `EnsureAsync` после `ALTER USER` делает то же для своего логина.
На :5443 после запуска 2026-11-26 в журнале «Пароли логинов печати в кэше MySQL: 7 из 7».
Восстановление кэша при перезапуске только MySQL реализовано в БАГ-1.2 вместо опроса из БАГ-1.1;
проверка именно с перезапуском MySQL остаётся в приёмке БАГ-1.2.
**Причина (проверено):** GoLabel жёстко задаёт `SslMode=none` и не разрешает получение RSA-ключа
(`QLabel.cs:7144`, `dbProperty.cs:44` в `C:\GGA1C\golabel-src`). Полную проверку
`caching_sha2_password` без TLS/RSA он не проходит — входит, только пока у сервера есть кэш
пароля. Кэш чистит перезапуск MySQL (был 25.10), `FLUSH PRIVILEGES`, `ALTER USER`. Ошибка:
`authentication method "caching_sha2_password" failed ... allowpublickeyretrieval=true`.
**Заплатка:** по разу вошёл каждым логином печати по TLS (`mysql --ssl-mode=REQUIRED`) — кэш
заполнен, вход без TLS проходит. Слетит при следующем перезапуске MySQL.
**Варианты:** (а) хаб сам «прогревает» кэш — `PrintConnectionWorker` раз в N минут входит
каждым логином печати по TLS (пароли у хаба есть); глобальные настройки MySQL не трогаем;
(б) логины печати на `mysql_native_password` — в 8.4 плагин выключен, нужно `mysql_native_password=ON`
в `my.ini`, перезапуск MySQL и правка `MySqlPrintLoginService` (в MySQL 9 плагина уже нет).

### П1. Баг: окно входа Keycloak при синхронизации из виджета
**Статус:** причина найдена; исправление отложено до П1.1. Боевой Keycloak не меняем.
Фоновое продление токенов и keep-alive вкладки отклонены: решение должно работать в новой вкладке,
пока действительна сессия шлюза, даже если сессия Keycloak истекла.

только по нажатию; `KEYCLOAK_IDENTITY` сессионная, после перезапуска браузера её нет. Куки
во фрейм доходят (`SameSite=None; Secure`, все три адреса — один сайт). Варианты с изменением
таймаутов или продлением токена не приняты; дальше — маршрут `/sync` (П1.1).
**Читать:** `docs/printing/decisions.md` (раздел «Баг»), `docs/platform/accounts.md`,
`docs/platform/stand.md` (Keycloak), код виджета `C:\widget_report_grist\index.html` (только
чтение, ~2600–2680), `Domain/Keycloak/KeycloakTokenVerifier.cs`.
**Цель:** найти, почему не проходит тихий вход, и убрать всплывающее окно при синхронизации.
**Готово, когда:** при действующей сессии шлюза вызов из новой вкладки Grist проходит без
повторного входа в Keycloak; при истёкшей сессии виджет показывает явное действие «Войти».
**Не делать:** не править виджет самим — правку оформить промптом для чата виджета; не менять
настройки реалма без согласования.
**Как:** systematic-debugging — сначала воспроизвести и измерить (время жизни сессий реалма,

### БАГ-1.2. Прогрев кэша паролей печати по событию запуска MySQL, без опроса
**Статус:** реализация готова. На :5443 проверены подписка 7036 и прогрев 7 из 7 при запуске
хаба (2026-11-26); обработка события ранее проверена на другой службе без остановки MySQL.
- [ ] **Приёмка с MySQL:** в согласованное окно при работающем хабе перезапустить службу MySQL
  и убедиться, что после события 7036 прогрелись все активные логины и GoLabel снова подключается
  без перезапуска хаба. До отдельного согласования службу не перезапускать.
**Как сделано:** `Blazor/Printing/MySqlStartWatcher.cs` — при старте хаба один прогрев
(`PrintLoginCacheWarmer`), затем `EventLogWatcher` на журнал System с фильтром
`MySqlStartEvent.XPath` (провайдер Service Control Manager, 7036, `param1` = отображаемое имя службы,
`param2` = `running` — латиницей, не переводится; проверено: фильтр находит запуски MySQL 18.10 и
25.10). По событию — пауза 5 с, прогрев; ни один логин не вошёл или ошибка — повтор каждые 10 с, до 6
попыток; прогревы не пересекаются. Журнал недоступен — предупреждение «Нет подписки на журнал
System…», остаётся прогрев при старте, хаб не падает. Настройки: `PrintLogins:CacheWarmup` (true),
`PrintLogins:MySqlServiceDisplayName` ("MySQL"). Работает и при `Workers__Enabled=false` (только вход
логинами по TLS). Проверка Uptime из `PrintConnectionWorker` убрана (работник снова только убирает

### БАГ-1.1. Кэш паролей печати после перезапуска одного MySQL
**Статус:** заменено БАГ-1.2 (2026-10-29: опрос Uptime убран, прогрев по событию 7036). Было: **Как сделано:** `PrintConnectionWorker` (тик 2 мин, первый тик — сразу при старте,

### БАГ-2. Ошибка MySQL раз в час: `You can't specify target table 'o' for update in FROM clause`
**Статус:** готово (`a493467`). На живом :5443 после перезапуска 2026-11-26 зафиксированы
три часовых запуска чистки токенов без ошибки 1093. Удаление подходящих записей и сохранение
остальных проверены тестами `TokenPruneTests`. **Причина:** фоновая задача ABP
`TokenCleanupBackgroundWorker` (раз в час) → `EfCoreOpenIddictTokenRepository.PruneAsync` строит
`DELETE FROM OpenIddictTokens WHERE Id IN (SELECT … FROM OpenIddictTokens …)` — MySQL такой подзапрос
к удаляемой таблице не разрешает. В журнале с 18.10 — 248 падений; чистка авторизаций после неё не
запускалась. **Исправление:** `EntityFrameworkCore/OpenIddict/MySqlOpenIddictTokenRepository.cs`
подменяет репозиторий (`ReplaceServices`): тот же отбор отдельным SELECT, удаление пачками по 500
номеров (`WHERE Id IN (список)`). Тесты `TokenPruneTests` (подмена и отбор: старые отозванные и
просроченные удаляются, живые и свежие остаются; на SQLite — сама ошибка MySQL там не
воспроизводится). На стенде таблица `OpenIddictTokens` сейчас пуста (0 строк), удалять нечего.
**Цель:** найти, какая фоновая задача её даёт (похоже на чистку токенов OpenIddict — удаление из
таблицы с подзапросом к ней же, что MySQL не позволяет) и исправить, не ломая вход.
