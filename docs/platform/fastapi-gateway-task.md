# Задача для шлюза db.mp-lab.ru: маршрут `/sync` к хабу GGA1C.Sync

Черновик от 2026-10-28. Адресат — программисты FastAPI-шлюза перед боевым Grist.

## Зачем

Хаб GGA1C.Sync (внутренний сервис на Windows Server) печатает этикетки и наклейки по кнопке из
виджета Grist **от имени конкретного человека**. Хабу нужно надёжно знать, кто нажал.

Сейчас это невозможно без шлюза:

- Пользователь входит в шлюз через Keycloak (realm `master`, клиент `fastapi-client`), дальше
  шлюз держит **свою** сессию (20+ дней). Сессии Keycloak у человека при этом нет — проверено:
  прямой переход на `/keycloak/realms/master/.../auth` показывает окно входа, хотя Grist открыт.
  Поэтому виджет не может тихо получить токен Keycloak, а окно входа при каждой печати
  неприемлемо.
- Grist не отдаёт виджету личность в проверяемом виде.
- Вызов хаба по его собственному адресу из страницы `https://db.mp-lab.ru` браузер режет
  (mixed content / сертификат).

Знает человека только шлюз. Поэтому просим один новый маршрут. **Настройки Keycloak,
существующие маршруты и вход в Grist не меняются.**

## Что сделать в шлюзе

### 1. Маршрут

Все запросы `https://db.mp-lab.ru/sync/{path}` — любой метод, query, тело — после проверки
обычной сессии шлюза проксировать на `{HUB_URL}/{path}`.

- `HUB_URL` — внутренний адрес хаба, задаётся переменной окружения шлюза (значение сообщим).
- Тело — потоком; разрешённый размер — **не меньше 64 МБ** (PDF-шаблоны бывают по 15 МБ).
- Таймаут ответа хаба — 120 с.
- **WebSocket**: проксировать upgrade для `/sync/_blazor` (и вообще любые WebSocket под `/sync/`).
  Страницы хаба (редактор шаблонов) работают на Blazor Server, без WebSocket они не оживут.
- Заголовки и куки ответа хаба (`Set-Cookie`, `Location`) передавать браузеру без изменений.

### 2. Без сессии

- Запросы страниц (браузер переходит по ссылке, `Accept: text/html`) — как сейчас: 307 на вход.
- Запросы API (`fetch` из виджета: `Accept: application/json` или заголовок
  `X-Requested-With: fetch`) — **401 с JSON** `{"error":"login_required"}` вместо 307. Иначе
  `fetch` молча идёт по редиректу на страницу Keycloak, и виджет не может показать понятное
  сообщение.

### 3. Защита от подделки

- **Удалить из входящего запроса** все заголовки, начинающиеся с `X-GGA1C-` (их может прислать
  кто угодно).
- Добавить два заголовка:

| Заголовок | Значение |
|---|---|
| `X-GGA1C-User` | base64url (без `=`) от JSON в UTF-8: `{"sub": "...", "email": "...", "name": "...", "preferred_username": "...", "iat": 1730140000, "exp": 1730140060}` |
| `X-GGA1C-Signature` | base64url (без `=`) от `HMAC-SHA256(SECRET, <значение X-GGA1C-User как строка ASCII>)` |

- `sub` — **обязателен**, это `sub` пользователя из ID-токена Keycloak, полученного шлюзом при
  входе (по нему хаб связывает человека; почту и логин человек может сменить, `sub` — нет).
  `email`, `name`, `preferred_username` — из того же ID-токена, если есть.
- `iat` — текущее время (Unix, секунды), `exp = iat + 60`.
- `SECRET` — случайные 32+ байта, переменная окружения шлюза (`GGA1C_SYNC_SECRET`). Такое же
  значение у хаба. Передаём вне репозиториев.

Пример (Python):

```python
import base64, hashlib, hmac, json, time

def b64url(data: bytes) -> str:
    return base64.urlsafe_b64encode(data).rstrip(b"=").decode("ascii")

def gga1c_headers(user: dict, secret: bytes) -> dict:
    now = int(time.time())
    payload = {"sub": user["sub"], "email": user.get("email"), "name": user.get("name"),
               "preferred_username": user.get("preferred_username"), "iat": now, "exp": now + 60}
    value = b64url(json.dumps(payload, ensure_ascii=False, separators=(",", ":")).encode("utf-8"))
    signature = b64url(hmac.new(secret, value.encode("ascii"), hashlib.sha256).digest())
    return {"X-GGA1C-User": value, "X-GGA1C-Signature": signature}
```

### 4. Прочие заголовки

`X-Forwarded-For` (адрес клиента **без порта**), `X-Forwarded-Proto: https`,
`X-Forwarded-Host: db.mp-lab.ru`, `X-Forwarded-Prefix: /sync`.

## Как проверить (критерии приёмки)

1. Без входа: `curl -H "Accept: application/json" https://db.mp-lab.ru/sync/api/ping` → 401 с
   `{"error":"login_required"}`; без этого заголовка в браузере — переход на вход Keycloak.
2. С входом: запрос из браузера на `https://db.mp-lab.ru/sync/api/whoami` (служебный адрес хаба,
   вернёт полученную личность) показывает ваш `sub` и почту.
3. Подделка: запрос с собственным заголовком `X-GGA1C-User` доходит до хаба без него (хаб
   отвечает «нет подписи» или видит заголовок, выставленный шлюзом).
4. WebSocket: страница `https://db.mp-lab.ru/sync/` открывается и работает (кнопки отвечают).
5. Файл 20 МБ уходит POST-ом на `/sync/api/...` без ошибки размера.

## Что делаем мы (сторона хаба)

- Принимать `/sync` как базовый путь (`PathBase`), выдавать служебные `GET /api/ping` и
  `GET /api/whoami`.
- Проверять `X-GGA1C-Signature` (HMAC-SHA256, сравнение за постоянное время), `exp` с допуском
  ±60 с; без подписи или с неверной — 401.
- Принимать такие запросы только с адреса шлюза (настройка хаба).
- По `sub` находить учётку человека (как при входе через Keycloak сейчас) и выполнять действие от
  его имени; неизвестный `sub` — заводить учётку, отключённую — отказ.
- Виджет в бою обращается к `https://db.mp-lab.ru/sync/...` с того же адреса — без токенов и окон
  входа.

## Открытые вопросы

- Внутренний адрес хаба в бою (`HUB_URL`) и доступ шлюза к нему по сети.
- Кто генерирует и как передаёт `SECRET`.
- Хранит ли шлюз claims из ID-токена после входа (нужен минимум `sub`).
