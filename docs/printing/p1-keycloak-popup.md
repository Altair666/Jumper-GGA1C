# П1. Окно входа Keycloak при синхронизации — разбор

Разбор 28.10.2026, только чтение: настройки Keycloak, Grist, IIS и виджет не менялись.
Карточка — `docs/roadmap.md`, П1.

## Коротко

Окно не «костыль, сработавший по ошибке», а честный исход: в момент синхронизации **сессии
Keycloak у человека уже нет**, и войти молча не из чего. Причины:

1. **Сессия Keycloak живёт 30 минут простоя, сессия Grist — 90 дней.** Grist ходит в
   Keycloak один раз, при входе, и дальше держит свою куку `grist_core`; сессию Keycloak он не
   продлевает. Через 30 минут без обращений к Keycloak она умирает, а Grist продолжает работать.
2. **Виджет не продлевает сессию сам.** Токены — только в памяти, `refresh_token` используется
   лишь в момент нажатия «Синхронизировать». Срок `refresh_token` = те же 30 минут простоя
   сессии. Прошло больше 30 минут с прошлой синхронизации (или с входа в Grist) — refresh
   отвергается, тихий вход получает `login_required`, открывается окно.
3. **После перезапуска браузера сессии нет вовсе:** кука `KEYCLOAK_IDENTITY` сессионная (без
   `Max-Age`, «Запомнить меня» в реалме выключено), а Grist при этом остаётся залогиненным.
   Первая синхронизация за день почти гарантированно открывает окно.

Куки во фрейм **доходят** — гипотеза «браузер не отдаёт куку Keycloak во фрейм» не
подтвердилась (см. ниже). Код виджета усугубляет картину, но не вызывает её: ответ
`login_required` он не распознаёт и ждёт 4 секунды, а потом открывает окно уже без
пользовательского жеста.

## Доказательства

### Настройки реалма `test` (admin REST API, 28.10.2026)

| Параметр | Значение |
|---|---|
| SSO Session Idle | **1800 с (30 мин)** |
| SSO Session Max | 36000 с (10 ч) |
| Client Session Idle / Max | 0 / 0 (берутся из SSO) |
| Access Token Lifespan | 300 с |
| Remember Me | **выключено**; Remember-me Idle/Max = 0 |
| Offline Session Idle | 30 дней (виджет `offline_access` не просит) |
| Revoke Refresh Token | выключено |
| Сохранение событий (`eventsEnabled`) | выключено, события только в лог `jboss-logging` |

Клиент `gga1c-widget`: публичный, standard flow, PKCE `S256`, redirect URI и web origin
`https://192.168.88.238:5443` есть, клиентские scope по умолчанию
`web-origins acr roles profile email`. Клиент `grist`: конфиденциальный, redirect
`https://192.168.88.238:8444/*`. Ошибок в настройке клиентов, мешающих тихому входу, нет.

Ответ токен-эндпоинта для `gga1c-widget` (вход curl'ом под `tester`):
`expires_in: 300`, **`refresh_expires_in: 1800`**, `refresh_token` типа `Refresh`
(не offline), `exp - iat = 1800`.

### Grist

`/opt/grist/grist-up.sh` не задаёт `COOKIE_MAX_AGE`; в коде Grist
(`_build/app/server/lib/gristSessions.js`) значение по умолчанию —
**`90 * 24 * 60 * 60 * 1000` (90 дней)**, `sameSite: "lax"`. Обновления токенов Keycloak в
`OIDCConfig.js` нет: после входа сессия Grist от Keycloak не зависит.

### Куки Keycloak (реальные `Set-Cookie`, вход curl'ом через `https://192.168.88.238:8443`)

```
AUTH_SESSION_ID=…;  Path=/realms/test/; Secure; HttpOnly; SameSite=None
KEYCLOAK_IDENTITY=…; Path=/realms/test/; Secure; HttpOnly; SameSite=None      ← без Max-Age
KEYCLOAK_SESSION=…;  Path=/realms/test/; Max-Age=36000; Secure; SameSite=None
```

Все `SameSite=None; Secure`, то есть уходят и во фрейм. Вдобавок Grist (`:8444`), виджет
(`:5443`) и Keycloak (`:8443`) — один IP и одна схема: для браузера это **один сайт** (порт в
понятие «сайт» не входит), куки тут не сторонние и под блокировку сторонних кук не попадают.
`KEYCLOAK_IDENTITY` без `Max-Age` — сессионная кука: закрытие браузера её стирает (если в
браузере не включено восстановление вкладок, которое сессионные куки сохраняет).

### Тихий вход curl'ом (тот же запрос, что строит `_kcAuthUrl`)

| Запрос | Ответ |
|---|---|
| `prompt=none` с куками живой сессии | `302 → …index.html?state=…&code=…` — тихий вход работает |
| `prompt=none` без кук | `302 → …index.html?error=login_required&state=…` |
| `prompt=none` с куками, через 34 мин простоя | **`302 → …index.html?error=login_required&state=…`** |
| `refresh_token` той же сессии, через 34 мин простоя | **`400 {"error":"invalid_grant","error_description":"Token is not active"}`** |
| вторая сессия: refresh на 25-й минуте (`200`, `refresh_expires_in: 1800`), затем `prompt=none` на 37-й | **`302 → …index.html?state=…&code=…`** — тихий вход прошёл |

Первые две строки «после простоя» — баг, воспроизведённый без браузера: через 30+ минут
простоя отказывают и refresh, и тихий вход, остаётся только окно. Последняя — доказательство,
что продление refresh'ем держит сессию: обращение к токен-эндпоинту сдвигает отсчёт простоя.
Отказ refresh на 34-й минуте оставил в логе Keycloak ту же строку, что и случаи 19 и 20 октября.

### Лог Keycloak (`docker logs keycloak-test`; время в логе — UTC, местное = UTC+3)

```
2026-10-28 13:43:42 REFRESH_TOKEN_ERROR clientId="gga1c-widget" error="invalid_token" reason="Token is not active"   ← опыт выше, 34 мин простоя
2026-10-19 08:05:21 REFRESH_TOKEN_ERROR clientId="gga1c-widget" error="invalid_token" reason="Token is not active"
2026-10-20 10:53:26 REFRESH_TOKEN_ERROR clientId="gga1c-widget" error="invalid_token" reason="Token is not active"
2026-10-20 10:53:33 LOGIN_ERROR clientId="gga1c-widget" error="invalid_user_credentials" redirect_uri=".../widget_report_grist/index.html" username="a.morozov@test.local"
```

Строки 19 и 20 октября — тот же баг в живую: refresh отвергнут как просроченный, через 7 секунд — неверный пароль,
введённый в окне входа. Отказ `prompt=none` → `login_required` Keycloak в лог **не пишет** (проверено:
запрос без кук в логе не оставил строки), так что отсутствие таких строк ничего не доказывает.

### Код виджета (`C:\widget_report_grist\index.html`, v0.53.0; копия в `C:\GGA1C\widget` совпадает побайтно)

- `kcGetToken()` (~2664): access token жив → отдаёт `idToken`; иначе один раз пробует
  `refresh_token`; при ошибке — `_kcSilentLogin`, при ошибке — `_kcPopupLogin`. Порядок
  правильный, но всё происходит **только по нажатию** — фонового продления нет.
- Перехват ответа (~620, `_KC_CALLBACK`) срабатывает лишь при `code` и `state`. Ответ
  `?error=login_required&state=…` не распознаётся: родителю ничего не уходит, а в скрытом
  фрейме **запускается весь виджет** (`DOMContentLoaded` → `initDate`, `initGrist`, …;
  в `<head>` этой копии ещё и 840 КБ `grist-plugin-api.js`).
- Неудача тихого входа = таймаут 4 с (`_kcSilentLogin`, ~2639). К моменту `window.open`
  прошло: запрос refresh + 4 с, а браузер разрешает окно только вскоре после жеста (в
  Chromium — около 5 с; на стенде не замерялось) — окно может быть заблокировано, у виджета
  на этот случай есть тост «Всплывающее окно заблокировано…».

## Что предлагается

Окно нельзя убрать совсем: если сессии Keycloak нет, войти без ввода пароля нечем. Можно
сделать, чтобы её почти никогда не было «нет» в рабочее время, и чтобы окно появлялось только
в этом честном случае.

### 1. Реалм `test` (и тот же набор потом в боевом Keycloak) — нужно согласие пользователя

- **SSO Session Idle: 30 мин → 8–12 ч** (рабочая смена). Одно это закрывает критерий карточки
  «40+ минут простоя».
- **SSO Session Max: 10 ч → 12–24 ч**, чтобы смена не обрывалась.
- По желанию — **Remember Me** включить с Remember-me Idle ≈ 7 дней и Max ≈ 30 дней: тогда
  `KEYCLOAK_IDENTITY` должна стать постоянной и пережить перезапуск браузера (при входе в Grist
  надо ставить галочку) — по документации Keycloak, на стенде **не проверено**.

Отзыв доступа не слабеет: отключённому в Keycloak человеку Keycloak не должен выдать ни refresh,
ни тихий вход (на стенде **не проверено** — проверить при правке реалма), а хаб и так сверяет
учётки раз в час (`KeycloakSyncWorker`, см. `docs/platform/accounts.md`).

### 2. Виджет — промпт для отдельного чата

См. раздел «Промпт для чата виджета» ниже. Суть: фоновое продление `refresh_token`, разбор
`error=` в перехвате ответа, отказ от 4-секундного ожидания, окно — только по явной кнопке.

### 3. Хаб — сейчас ничего

Хаб проверяет только подпись, издателя, срок и `azp` (`KeycloakTokenVerifier`, `ClockSkew` 1
мин); к окну он отношения не имеет. Если и после пунктов 1–2 окно будет мешать, следующий шаг —
длинная сессия на стороне хаба (виджет отдаётся с того же адреса `:5443`, кука хаба уходит из
фрейма без ухищрений; хаб держит refresh/offline-токен у себя). Это заметная доработка, связана
с П7 (вход в хаб через Keycloak), без отдельного решения не делать.

### Попутно найдено

В `C:\GGA1C\widget` нет папки `vendor/`: `https://192.168.88.238:5443/widget_report_grist/vendor/pdf.min.js`
отвечает 404 (в репозитории виджета `vendor/` есть). К П1 не относится, но редактор PDF на
стенде так работать не будет.

## Что нужно от пользователя

1. **Согласие на правку реалма** (пункт 1) — значения idle/max и включать ли Remember Me.
2. Подтвердить в браузере на своём рабочем месте: DevTools → Network, отфильтровать `auth?`,
   нажать «Синхронизировать» после 40+ минут простоя. Ожидается ответ `302` с
   `error=login_required` в `Location` (а не отсутствие кук в запросе). В Application → Cookies
   для `https://192.168.88.238:8443` — нет `KEYCLOAK_IDENTITY` или она уже недействительна.

## Промпт для чата виджета

```
Репозиторий C:\widget_report_grist, файл index.html (v0.53.0), блок KEYCLOAK PKCE AUTH
(~2565–2680) и перехват ответа KEYCLOAK CALLBACK INTERCEPTION (~614–630).

Проблема: при «Синхронизировать» всплывает окно входа Keycloak. Разбор — в репозитории хаба
GGA1C.Sync, docs/printing/p1-keycloak-popup.md: refresh_token живёт 30 мин простоя сессии
Keycloak, а виджет пользуется им только по нажатию; через 30+ мин refresh и prompt=none
отказывают, и открывается окно. Реалм тоже поправят, но виджет должен сам держать сессию.

Сделай:
1. Фоновое продление. После любого успешного получения токенов (_storeKcTokens) запоминай
   refresh_expires_in и ставь таймер: обновлять токены по refresh_token примерно каждые
   min(4 мин, refresh_expires_in/2). Плюс на document.visibilitychange (вкладка снова видна) —
   немедленное обновление, если с прошлого прошло больше 4 мин (таймеры скрытых вкладок
   браузер притормаживает, а во сне ПК они стоят). Ошибка фонового
   обновления: kcSession = null, без окон и без тостов. Таймер один, не плодить.
2. Перехват ответа: если в location.search есть error и state (без code) — отправь родителю
   { type: 'kc-auth-error', error, state } и так же, как для code, не запускай остальную
   инициализацию (_KC_CALLBACK = true). Для opener — то же, окно закрыть.
3. В listener message: на kc-auth-error с совпавшим state — reject(new Error(error)).
   _kcSilentLogin тогда падает сразу с login_required; таймаут 4 с оставь только как страховку.
4. Окно входа не открывать автоматически из kcGetToken после неудачи тихого входа (жест
   пользователя к этому моменту уже истёк, окно режется блокировщиком). Вместо этого бросай
   ошибку 'login-required', а в обработчике синхронизации показывай в кнопке/тосте
   «Нужно войти в Keycloak» с кнопкой «Войти», которая по клику вызывает _kcPopupLogin и
   затем повторяет синхронизацию.
5. Поднимай VERSION, остальное не трогай. Проверка: войти, подождать 35+ минут с открытой
   вкладкой, «Синхронизировать» — окна быть не должно; в Network — периодические POST
   /token с grant_type=refresh_token и 200.
```
